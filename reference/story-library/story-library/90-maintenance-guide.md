# Story Library 维护指南 v3.1

> 更新：2026-08-26  
> 目标：让剧情库做到“先事实、后解释；先正文、后索引；先验收、后宣告完成”。

## 0. 维护原则

Story Library 不是新闻摘要，也不是社区猜测仓库。每次更新都必须同时满足：

1. **时效正确**：只把已经正式实装的内容写进事实层。
2. **信息分层**：区分版本发布顺序、世界内时间、角色当时认知、后续反转后的重解释。
3. **证据可追溯**：正式版本章必须能回到具体官方公告、游戏内任务名或完整流程。
4. **不静默覆盖**：后续反转只能修改解释，不能删除旧版本角色当时真实掌握的信息与已经发生的后果。
5. **工程一致**：正文、manifest、前端目录、根索引必须在同一轮验收中保持一致。

统一事实标签：

- 【官】游戏内或官方公开资料直接确认。
- 【证】多个已实装一手信息可以稳定拼合。
- 【推】证据较强，但仍可能被后续剧情推翻。
- 【未】作品明确留下、当前尚未解释。
- 【可能未来】只用于预知、演算、梦境未来分支等不能当作已发生历史的内容。

## 1. 正确的大版本更新顺序

**不要先改 `00-index.md`。** 根索引是“完成状态公告”，必须最后更新。

正确顺序：

```text
① 确认版本已经正式上线
→ ② 锁定校对日期与版本结束/复核日期
→ ③ 收集官方更新公告、任务名、完整实机/文本锚点
→ ④ 写/更新 versions 正文
→ ⑤ 更新 timeline / characters / factions / mysteries / video-hooks
→ ⑥ 更新游戏 README
→ ⑦ 更新 FILE_MANIFEST.md（仅当路径新增/删除）
→ ⑧ 更新 reference/story-library.html 的离线 fallback（若新增正式路径）
→ ⑨ 更新 CURRENT_STATUS.json
→ ⑩ 运行 Story Library 自动检查
→ ⑪ diff 验收：只改预期文件
→ ⑫ 最后更新 00-index.md
→ ⑬ PR → merge
→ ⑭ 从 main 回读：正文 / index / manifest / 网页入口
```

如果中途断线，允许分支保持“未完成”，但**不允许根索引提前写成已完成**。

---

## 2. 新版本上线前后如何切换状态

### 版本尚未上线

只能写在：
- watchlist / 未来观察项；
- mysteries 的【未】；
- README 的“下一版本已官宣”区域。

禁止：
- 把预告演出当作已发生剧情；
- 把测试服文本当正式剧情；
- 在 `00-index.md` 写“已实装至下一版本”。

### 正式上线当天

先确认官方版本号和开拓/主线任务已经永久开放，再执行：

- 旧“当前版本”改为历史版本；
- 新版本建立正式档案；
- `CURRENT_STATUS.json` 更新 `current_version`、`verified_at`、`review_by`；
- README / overview / timeline / mysteries 的“当前边界”同步修改。

### 为什么需要 `review_by`

CI 无法联网判断“今天是否刚开新版本”，但可以检查我们自己承诺的复核期限是否过期。`CURRENT_STATUS.json` 的 `review_by` 到期后，自动检查会给出警告，提醒重新联网核对版本状态。

## 3. 正式版本剧情文件标准

推荐模板：

```md
# 版本号｜正式篇章名

> 游戏：
> 版本：
> 状态：当前已实装 / 历史已实装
> 实装日期：
> 校对日期：
> 世界内时间（必要时）：
> 事实标记：【官】｜【证】｜【推】｜【未】

## 0. 一页看懂
## 1. 前情局势
## 2. 事件链
## 3. 关键人物为什么这样做
## 4. 谁在什么时候知道什么
## 5. 阵营/关系变化
## 6. 世界观新增
## 7. 伏笔回收与新增
## 8. 后见重读（如有）
## 9. 容易误读 / 禁止写死
## 10. 主题
## 11. 前后章连接
## 来源锚点
```

不要求机械套满所有标题，但正式章至少必须回答：

**发生了什么 → 为什么发生 → 人物为何选择 → 新信息改变了什么 → 什么仍然未知。**

---

## 4. 来源锚点最低标准

每个正式主线版本章至少应尽量提供：

1. **1 个官方 URL**：版本更新、任务说明、官方回顾或官方剧情PV；
2. **明确的游戏内任务/章节名**；
3. 如官方页不足以核对具体演出，再补 **1 个完整无剪辑实机或文本索引**。

社区 Wiki / 攻略的正确用途：
- 找任务名；
- 找遗漏节点；
- 对照任务顺序；
- 发现值得回查的细节。

不能单独用于写死：真实身份、亲属关系、死亡状态、时间机制、幕后组织、测试服设定。

---

## 5. 时间线必须分层

遇到以下内容时，禁止机械按版本号排成唯一时间线：

- 倒叙；
- 梦境；
- 记忆重演；
- 预知未来；
- 模拟/演算；
- 时间回返；
- 身份冒用；
- 后续揭示“当时角色并不知道”。

至少区分：

```text
发布顺序
世界内真实顺序
角色当时认知顺序
后续重解释
```

《异环》1.2、翁法罗斯循环、匹诺康尼梦境、二相乐园画中世界都属于这一类。

---

## 6. 兼容页规则

旧路径可以保留，避免外部链接失效，但必须满足：

- 正文第一屏写明“兼容导航 / 历史总览”；
- 指向新的正式章节；
- 加入前端 `hiddenLegacyDocs`，不和正式章同时出现在主导航；
- 不再承担“当前版本正文”职责。

禁止为了清爽直接删除仍可能被旧链接引用的文件。

---

## 7. FILE_MANIFEST 与前端目录

`FILE_MANIFEST.md` 是在线目录的事实源。

新增/删除 Markdown 路径时必须更新 manifest。

`reference/story-library.html` 有两层目录：

1. **LIVE**：在线从 manifest 读取；未知新文件会读取 Markdown 第一行 `# 标题` 生成友好标签。
2. **FALLBACK**：manifest 失败/离线时使用内置目录。

所以新增正式章节时，仍应把 fallback 同步到当前版本，保证完全离线时不会退回数月前目录。

---

## 8. 自动检查

运行：

```bash
npm run check:story
```

或：

```bash
npm run check
npm test
```

Story Library 检查至少覆盖：

- manifest 重复路径；
- manifest 指向不存在文件；
- 实际 Markdown 漏登 manifest；
- 五款维护游戏缺少 README / 00–05 核心索引；
- 正式版本章缺少来源区（警告）；
- `CURRENT_STATUS.json` 与根 index / 游戏 README 的版本号不一致；
- `review_by` 已过期（警告）；
- 已知兼容文件没有被前端隐藏；
- 前端缺少 manifest LIVE 同步逻辑。

结构性错误必须让检查失败；来源密度和复核到期先以 warning 提醒，避免旧资料库一次性全红。

---

## 9. PR 前最终验收清单

只允许在以下全部成立时把根索引写成“完成”：

- [ ] 当前版本已正式上线。
- [ ] 正文已落盘。
- [ ] 时间线/人物/谜团已同步。
- [ ] 来源锚点存在。
- [ ] manifest 与实际路径一致。
- [ ] fallback 目录能显示新增正式章。
- [ ] `npm run check:story` 通过。
- [ ] 分支 `behind 0` 或已经无损重放到最新 main。
- [ ] diff 没混入其它游戏/业务文件。
- [ ] PR 已创建并可安全合并。
- [ ] merge 后从 `main` 回读验证。

**根 index 是验收结果，不是任务计划。**
